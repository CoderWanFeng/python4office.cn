## 二、让 AI 部署网站，危险的从来不是它会不会写代码

很多人一提「AI 部署网站」，第一反应是「AI 能不能把代码写对」。这是把部署想成了一个技术问题。

**部署不是技术问题，它是一次授权。**

拆开看，AI 替你部署，本质上替你做了三件事：

| 它替你做的 | 实际发生了什么 | 出了事能撤回吗 |
|---|---|---|
| 拿到凭证 | 你的 Token / 密钥 / 登录态被交给命令行 | 凭证泄露了要手动 revoke |
| 推送内容 | 目录里的东西被搬到一个外部平台 | 已经公开的内容，收不回来 |
| 覆盖线上 | 线上那一版被新的一版替换 | 要回滚，要走流程 |

![AI 替你部署网站，本质上是三次授权](https://raw.githubusercontent.com/CoderWanFeng/img-cdn/master/261117-site-skill-actions.jpg)

*图：AI 替你部署网站，本质上是三次授权 · 晚枫自制插图*

第一步是**开门**，第二步是把东西搬出去，第三步是让线上换掉。

三步全是不可逆动作。所以「让 AI 部署」这件事的风险，从来不在它生成的代码合不合格，而在**你把哪把钥匙交给了它、它把什么推到了公网上**。

**个人项目推错了，删掉重来；公司项目推错了，那是一张事故单。**

## 三、公司网站为什么更危险

同样一个动作，放在公司项目上，代价要翻好几倍。

**第一，内容不是你的。** 源码里可能有客户名单、内部文档、没发布的定价、没官宣的方案。推到一个公开地址上，就不是「可能泄露」，而是**已经泄露**。

**第二，钥匙是公司的。** Cloudflare 要 API Token，腾讯云 CloudBase 要 SecretId 和 SecretKey，GitHub 要登录态或 SSH Key。这些是长期有效的凭证，一旦交给命令行，它就会出现在 shell 历史、部署日志、报错信息里。

**第三，门是公司的。** 域名、云账号、备案、CDN 配置，全挂在公司名下。让 AI 拿着公司的钥匙推代码，出了问题，责任在你，不在 AI。

**第四，动作是有痕迹的。** 公司服务器上的每一次 push、每一次部署调用，都可能进审计日志。AI 帮你省下的几分钟点击，换来的是一次说不清来历的变更。

**第五，回滚不是按个键就行。** 个人项目回滚是 `git reset`；公司项目回滚要走发布流程、可能要改数据库、要通知相关的人。

所以我的立场很明确：**公司网站，不该让 AI 直接部署。**

## 四、我这个 Skill 是怎么处理这类风险的

「晚枫个人网站」Skill 现在是 v2.0.0。它的定位一直是两件事：**帮你把网站搭起来**，以及**告诉你怎样安全地部署**。

第二个「安全」，不是一句口号，它落在这几个具体机制上。

### 1. 先锁住路径：不让它在你电脑上乱写

创建项目之前，脚本会先跑一遍路径校验，直接拒绝这些目标：

- 路径里带 `..` 的越界写法；
- 根目录 `/`；
- 系统目录：`/System`、`/usr`、`/etc`、`/bin`、`/sbin`、`/var`、`/private`、`/boot`、`~/Library`，Windows 下的 `C:\Windows`、`C:\Program Files`；
- 符号链接指向系统目录的情况；
- 父目录不可写。

**这一步挡掉的，是「AI 手一滑在你系统目录里建了个项目」这种事。**

### 2. 建目录不覆盖：同名就换名

如果你指定的目录已经存在、里面还有东西，它不会覆盖，而是自动换一个名字：`-2`、`-3`，依次往后。（空目录可以直接用。）

覆盖旧项目这个动作，比部署危险得多，而且几乎无法撤销——被覆盖的文件不会自己长回来。

### 3. 动手之前必须过你这一关

第 5 步会把所有选项摆成一张清单：网站类型、技术栈、网站名称、描述、作者名、创建目录。

**只有你回复「确认」，它才会开始创建。**

这是整个流程里最便宜的一道保险：出错的成本从「已经建了一堆文件」降到「清单上多看了一眼」。

### 4. 部署的门槛写在明面上，不藏着

它内置 6 个部署平台，每个平台需要什么、有什么限制，都写在文档里，不靠猜：

| 平台 | 需要你先准备好的 | 你该知道的限制 |
|---|---|---|
| Netlify | 什么都不用（可匿名部署） | 匿名站点 1 小时内不认领就会被清理 |
| Surge.sh | 首次可免注册 | 国内访问偏慢 |
| Cloudflare Pages | API Token | 权限按官方文档配，别多给 |
| 腾讯云 CloudBase | 实名认证 + 环境 ID | 自定义域名在国内节点要备案 |
| Vercel | 登录账号 | 海外节点，国内访问会受影响 |
| GitHub Pages | gh CLI + 已登录 | **公开仓库才能用**，私有仓库要 Pro |

注意最后一行。**「用 Pages 上线」和「把代码放到公开仓库」是同一件事。** 公司项目如果没意识到这一点，就等于在最后一步把源码公开了。

还有一件事它不会替你做：**它不替你登录账号，也不替你生成 Token。** 凭证由你保管，Skill 只负责把流程跑完。

### 5. 上线之后必须验证，还要留痕

部署完不是结束。它会做两件事：

- **验证**：跑一遍连通性检查，确认那个 URL 真的能打开、标题是不是预期的那个；
- **留痕**：把平台、URL、部署时间、框架、产物目录写进 `.deploy-state.json`，下次要重新部署，直接复用，不用重新回忆。

**「没验证过的上线，不叫上线成功，只叫执行了命令。」**

### 6. 它明确不做的三件事

- **不做安全审计。** 它不会替你判断「这个目录里的东西能不能公开」；
- **不判断合规。** 备案、代码归属、数据出境，不在它的职责里；
- **不碰已经上线的项目。** 它的流程是从零建站，不是在生产环境上做变更。

**它想省掉的是「流程啰嗦」，不是「你的责任」。**

## 五、给普通人：先分档，再决定让 AI 走到哪一步

不是所有网站都危险，关键是分清三档：

| 你的项目 | 让 AI 走到哪一步 | 为什么 |
|---|---|---|
| 自己的练手站、作品集、简历页 | 放心让它一路部署到线上 | 内容本来就是公开的，推错了删掉即可 |
| 公司的官网、内容站 | **只让它做到本地预览 + 构建产物**，上线由人来点 | 内容与凭证都属于公司 |
| 已经在跑的生产系统 | 不要让 AI 直接动线上，走公司自己的发布流程 | 生产变更需要审计和回滚能力 |

![按项目类型分档，决定让 AI 走到哪一步](https://raw.githubusercontent.com/CoderWanFeng/img-cdn/master/261117-site-skill-tiers.jpg)

*图：按项目类型分档，决定让 AI 走到哪一步 · 晚枫自制插图*

如果你确实要部署公司项目，下面 5 条是底线：

1. **凭证不进对话。** Token 用环境变量传，别贴进聊天框、别写进仓库、别留在命令历史里。
2. **推之前先列一遍文件清单。** 确认将要公开的目录里，没有 `.env`、密钥、客户名单。
3. **默认 Private。** 公开仓库是「已公开」，不是「还没公开」。
4. **上线这一步由人来点。** 让 AI 把命令准备好、参数填好，最后一条你自己执行。
5. **上线后自己看一眼。** 打开那个 URL，确认是你的内容，不是别人的。

## 写在最后

那天沙龙上，四位讲师讲的是同一件事：**别把 AI 当问答机，把活交代清楚，它才会替你干。**

开放麦上那位朋友的分享，其实也符合这句话——活确实交代得很清楚。

只是有一类活，交代清楚了也不能直接交出去：**一旦出错，你没法重来。**

个人网站、公司官网、生产系统，风险不是一个量级。同样一句「帮我部署一下」，背后该站的人是不一样的。

**能撤销的活，放心交给 AI；不能撤销的活，人要站在中间。**
